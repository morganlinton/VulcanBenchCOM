How it works

Methodology

Real engineering tasks, gated on difficulty and decontaminated against model cutoffs, graded by deterministic hidden tests, with cost, time, and tokens measured right alongside the score.

01 · The principle

Evals based on real work, real engineering teams do.

Before diving into the methodology I have developed with VulcanBench, I think it probably makes sense to introduce myself. Hi, I’m Morgan, and I’m the Cofounder and CTO of Bold Metrics, an AI startup that helps some of the world’s leading apparel brands with fit and sizing. I lead an engineering team, and over the last 18 months we’ve gone head-first into agentic coding workflows.

What has been challenging for me as an engineering leader is knowing what benchmarks I can use to truly understand how a model will perform when my team uses it for the regular coding tasks we do every day. As I did a deeper dive into some of the current benchmarks out there, I found many of the evals had too many tasks that were things like puzzles or math problems, that didn’t reflect the kind of things my team would be doing with these models.

Looking on social media, I found a lot of people testing models by seeing how well a new model can build a working version of Flappy Bird or create an image of a pelican riding a bike, and well, yeah, that’s not as helpful for engineering teams like mine shipping production code that goes out to hundreds of millions of active users.

So I started benchmarking models myself, at first just testing our own engineering tasks across different models. Then I started to augment the effort level and had a bit of an aha moment. I realized that while so many model providers default to High effort, with the new class of models we now have, Low and Medium effort often produces the same result, faster, and cheaper.

The longer version of that story — the model bill that started it, and the routing idea it led to — is in why I started VulcanBench.

As I started to get deeper into model benchmarking for us, I realized that all of the Python scripts I had created were getting messy, I needed a more clean and organized way to run my benchmarks. And well, I’m a big Star Trek fan, that’s one of the reasons why we’re called Bold Metrics, i.e. to boldly go where no one has gone before ;) I knew I wanted the name of whatever tool I built to have the word bench at the end, and I also knew I wanted a tool that at its core was about honest and transparent benchmarks, and I immediately thought, Vulcans!

Yup, and that’s how VulcanBench was formed.

My general thinking is that any benchmark that just runs one pass, and doesn’t take into account things like token use, cost, and time, is leaving out some really important pieces to the puzzle. If I am comparing two models, and one is 5% better than the other, but that model also has an overthinking problem and uses 5x the number of tokens and takes much longer to solve problems, that would be important to know, right?

And that’s my mission with VulcanBench. Open source in every way, every single eval, and the source code for the benchmarking tool itself, all available for everyone to see, critique, and help improve.

As you can probably now understand from the journey I’ve been on to get here, I’m not some kind of benchmarking expert, and yes, there are a lot of people much smarter than me working on really interesting benchmarks. So if you find an issue with one of my benchmarks, tell me, or better yet, put in a PR and help fix it.

I am dedicated to helping my engineering team use the best models out there, and that means I need to run as many evals as I can, and keep updating them every week to get even better. I hope I am able to help other teams like us that are looking for benchmarks that reflect the kind of work we do every day.

02 · What a task is

A real ticket, handed off exactly as an engineer would receive it.

Tasks come in two shapes. The mined-PR format builds a task from a real merged pull request in a production open-source project (flask, sqlglot, aiohttp, urllib3, hono, zod, semver, jiff, chi, networkx, and more). The binary-parity format, described in the next section, replaces the readable defect with a compiled artifact. Both ship a starting repository, a set of hidden tests never shown to the agent, declarative fail_to_pass and pass_to_pass test commands, and a gold-patch reference solution.

The mined-PR format is the mid-band and regression tier, and it is where most of the corpus lives: the Coding Intelligence Index v1 suite carries 58 gold-verified tasks across Python, TypeScript, Go, Rust, and JavaScript, and the older v1/v3/v4 suites remain frozen and replayable for the reports already published against them.

1

Slice the repository

The repository is checked out at the pull request's base commit, the exact state a developer would face before the fix existed.

2

Hand off the ticket

The agent receives a terse issue describing the symptom plus the full working tree, and the standard toolset: list, read, edit, search, and run commands. The issue describes symptoms and requirements, never the file to edit or the shape of the fix.

3

Produce a patch

The agent works the problem until it believes it is done, within a step budget and a wall-clock sanity bound. Its diff is captured as the answer.

4

Grade it

The patch is scored by the project's own hidden tests, pass or fail, with time, tokens, and resource consumption recorded alongside.

03 · The frontier suite

When the defect is readable, models read it.

The mined-PR format ranks frontier models but does not stretch them: on the mid-band suite, Claude Opus 5 scores 96.4% pass@1. A defect that exists in readable source gets found by reading, so the hard part has to sit behind something the model cannot read. VulcanBench-SWE v4 is built on that principle.

The binary-parity format

Each task ships a compiled legacy binary, a written specification that has drifted out of sync with it, and a replacement implementation written from that specification. The job is to bring the replacement to byte-for-byte parity with the binary. The information needed to do that is in no source file; it has to be recovered from the binary itself.

Difficulty is an admission criterion, not something measured after the fact. Every candidate is run n=3 against two reference frontier models on their own subscription harnesses, and admitted only if the weaker reference (GPT 5.6 Sol on the Codex CLI) solves at most one of three runs and the stronger one (Claude Opus 5 on the Claude Code CLI) needs a median of ten minutes or more per run, or misses a run outright. Correctness gating is separate and absolute: the reference solution scores 1.0, the unmodified base scores 0.0, three consecutive identical runs, plus a build check that the reference matches the binary byte-for-byte across randomized input sweeps.

Opus 5 misses runs on six of the eighteen tasks, and spends half the tokens of the model scoring a nineteenth as much. The time columns are computed from recorded durations after the fact; no run is ever stopped by a cut.

A compact binary is not actually opaque

GPT 5.6 Sol defaults to disassembly on this task family and, on a small single-engine binary, reads the mechanics straight out of the assembly in four to thirteen minutes. What holds up against that isn't concealment, it's reconstruction burden: state spaces where fixing a hypothesis by differential fuzzing stays slow, and where an overgeneralized fix breaks the spec-faithful behavior the tests also check. Read the scores above as model-plus-strategy under each vendor's own harness, not as a ceiling on what the model can do.

Rejected candidates are recycled into the mid-band suite, and every admission verdict is recorded in the suite's candidate ledger.

04 · Decontamination

The fix must be genuinely novel, and stay that way.

A benchmark built from public code risks measuring memory, not reasoning. So provenance is labeled and checked, never assumed: every task declares a source, either hand-authored or oss, plus an explicit decontaminated boolean, and the validator enforces the claim.

Open-source tasks are built from pull requests merged after the evaluated models' training cutoffs, so the solution post-dates what any model could have seen, and every task records its upstream_merged date so the clean subset for a given model is a query rather than an archaeology exercise. Hand-authored tasks, including the whole binary-parity suite, are original scenarios written for VulcanBench now, not derived from any public repository, so they are decontaminated by construction. Where a task is sourced verbatim from an existing repository whose fix predates model cutoffs, it is honestly labeled decontaminated: false, and every result scored against it is flagged in the integrity section of the report.

Publication starts the contamination clock, so two mechanisms keep the claim honest over time. Every task carries a canary string and GUID in its metadata, absent from the task's repo/ tree by design, so a suite that has leaked into a training corpus can be detected rather than argued about. And the suites follow benchmark semantic versioning: adding, removing, or changing the environment of a task is a breaking change that bumps the version, and results are comparable only within one version. Every run summary records the suite version and a per-task content hash.

Suites also decay by design. When a new frontier generation lands, the frontier suite is re-gated, and any task the weaker reference now solves reliably, or where the stronger reference's median drops under ten minutes, is pruned out to the mid-band suite with the verdict logged. A benchmark that never removes tasks is quietly measuring something different every year.

05 · Grading

Deterministic hidden tests. No model judges another model.

By default a task's correctness comes from hidden tests that are deterministic and exact. The fail_to_pass tests are validated to fail on the base commit and pass on the merged fix; the pass_to_pass tests guard against regressions. If any pass-to-pass test breaks, the functional score is gated to zero regardless of how many new tests pass: a fix that breaks working behavior is not a fix.

Validation proves each task is real before it is ever used: the gold patch must solve it (functional score of exactly 1.0), the fail-to-pass tests must genuinely fail before the fix, and scoring must be identical over repeated runs. There is no LLM judge in the default path, no rubric, and no partial credit for plausible-looking diffs.

The exception, made explicit

A task may opt into an agentic grader when the point is to test terse, realistic prompts where the specification lives in the grader rather than the prompt. It judges the diff against hidden acceptance criteria, graded by a strong, independent model, never the model under test, by majority vote over several calls, and every such grader is itself evaluated for accuracy, self-consistency, and false-pass rate before it ships. Agentic grading is non-deterministic, so it is opt-in and never the default.

06 · The five metrics

Correctness is half the score. The rest is how you got there.

Every run produces five sub-scores on a 0–1 scale, combined into a weighted total. Functional correctness dominates, but a diff that passes tests can still be sloppy, insecure, or wasteful, and those are measured too.

Functional is pass/fail on the hidden tests. Quality runs real linters and complexity tools on the changed files. Security runs static analysis for introduced vulnerabilities. Efficiency maps token and step usage to a frugality score. Human-like is the only judged metric, an LLM ensemble, and it carries the least weight. The report tables on this site are graded functional-only, with judges disabled, so that no model's opinion touches the headline numbers.

07 · The execution boundary

Three modes, disclosed per run.

There is no longer one universal container, because there is no longer one kind of run. A raw-API run and a run through a vendor's own coding CLI have genuinely different boundaries, and pretending otherwise would be the dishonest option. Every run summary records which boundary applied.

Docker sandbox — the default for API runs

A non-root container with the network switched off and CPU and memory capped. Command execution and the functional verifier both run inside it, so the agent cannot reach the internet to fetch a known answer. Tasks with heavy dependency stacks use per-task images with the upstream package's dependencies preinstalled, so a run measures the model's engineering, not its ability to fight a package manager. It fails closed: if the daemon is unreachable the run errors rather than silently falling back to the host. Network isolation is the default; opting out is deliberate and recorded.

Vendor harness — for subscription runs

Claude Code, Codex, Cursor, Grok Build, and ZCode run under their own sandbox on the host, not ours: Codex's workspace-write, Claude Code's permission mode, Cursor's sandbox, a custom Seatbelt/Landlock kernel profile for Grok Build, and, for ZCode, no kernel sandbox at all. VulcanBench keeps task preparation, the captured diff, hidden verification, and scoring. Publication runs verify in Docker even when the agent phase does not.

Agent-in-container — opt-in

The newest mode runs the subscription CLI itself inside a container built from the sandbox base image, so the same resource band bounds the agent phase as well as verification. Authentication is a run-scoped copy of the host credentials, and the container, rather than the CLI's own sandbox, provides the write boundary.

Two leak channels, both real, both observed

An agent running on the host with broad tool access, against tasks derived from public merged PRs, leaks two ways. Blocking one does nothing about the other, and both showed up in live sweeps before they were closed.

The web. Every mined-PR task's fix sits at a known URL. In the first Cursor sweep, 46% of runs fetched their task's exact source pull request or fix commit, and the median patch of those runs matched the gold patch exactly.

The filesystem. A workspace inside the benchmark checkout lets an agent walk up into the task tree and read the gold patch and the hidden tests, the grader's answer key, not merely the upstream fix. In one sweep with the web already blocked, 46 runs read their own task's answer key, and all 46 solved.

1

Containment

The load-bearing defence. Harness runs get a workspace created outside the repository entirely, so no benchmark data exists anywhere above the agent's working directory. Enumerating forbidden paths is the same losing game as enumerating forbidden URLs.

2

Prevention

Web search and fetch tools are denied or removed outright, per harness, along with the browser plugin one of them enables by default. Cross-session memory is disabled everywhere, so repeat two cannot remember repeat one.

3

Detection

Every harness run carries an integrity audit over both channels, with verdicts from no_web and web_blocked through upstream_access and solution_retrieval, and from clean through answer_key_access. A run flagged on either channel is contaminated. The audit annotates; it never rescores.

Note what the audit is not. A rejected call is not access, and the audit has to correlate a tool call's start and completion before scoring it, an earlier version scored the start event alone and flagged four clean runs as contaminated, one of them as solution retrieval.

08 · Reasoning effort

A cheap dial that re-introduces separation.

Reasoning effort, the model's thinking-token budget, is a normalized control set to minimal, low, medium, high, extra-high, or max. It maps to each provider's native field where one exists, and subscription harnesses pass the supported labels through to their own CLIs. Holding a suite fixed and sweeping the dial turns a saturated benchmark into a discriminating one for free: the low-effort dropoffs below the high-effort ceiling are the signal.

A label that cannot be sent is never pretended. Providers document different enums, and several silently coerce a level they do not support into a neighbouring one, which would quietly turn a sweep into two identical columns. So each provider's mapping is explicit, an unsupported label is recorded as metadata without being sent, and where a CLI reports back the level it actually used, that value is read out of the CLI's own ledger and recorded next to the requested one.

The labels are not calibrated across vendors, and that matters. Effort is each provider's own scale: comparing two models at the same label compares each at its own setting, not a calibrated equivalence. So token counts always sit beside effort labels, and the per-task step budget is held identical across cells, so only the thinking budget moves.

09 · Economics

Cost is a result, not a footnote.

Every run records cost, wall-clock time, agent steps, and token usage. The headline efficiency metric is cost per solved task: total spend divided by tasks passed, which fairly charges a model for both its failures and its verbosity. This is the axis that keeps mattering after accuracy converges. Across the published reports, models tying on correctness have differed by 3× to 4× in cost and up to an order of magnitude in tokens, differences driven by how much each agent thrashes, especially when navigating large repositories.

How that number is derived depends on how the run was billed, and the two are kept in separate tracks.

API track. Cost is computed from each provider's published list prices and, where a provider applies an automatic prompt-cache discount, that discount is folded into the reported total, since a naive token count can overstate a run's true spend several-fold.

Subscription track. A run billed to a Claude, ChatGPT, Cursor, GLM, or Grok plan does not get to claim that included usage cost zero. Each run carries an economics receipt whose fields are recorded independently rather than summed into one comforting number: marginal cash caused by the run, measurable overage, a modeled share of the plan fee, the cash cost of independent grading, the counterfactual API-equivalent value of the tokens, and the provider-reported quota consumed. Every one of those carries a measurement-quality flag saying whether it is exact, provider-reported, estimated, or simply unavailable. One CLI streams no usage at all, so its API-equivalent value is recorded as unavailable rather than guessed.

The two tracks are never added into one claim. A subscription result includes the product's system prompt, context management, safety layers, tools, and possible model routing: it measures a model plus a harness, and it is labeled that way everywhere it appears.

10 · Refusals and infrastructure

A refusal is a failure. A broken machine is not.

When a model's safety classifier declines a benign, security-adjacent task, say a parser fix flagged as cyber content, the run is scored as a failure, with no fallback model configured. An engineering team whose model refuses to touch parser code experiences that as a failure, not a neutral abstention. It is invisible on conventional accuracy benchmarks and highly visible in practice, so VulcanBench records it as a first-class outcome.

The mirror image is treated as carefully in the other direction. A subscription quota running out mid-sweep, a verifier dependency missing from an image, a container killed for running out of memory: none of those are things the model did, and scoring them as functional zeros would silently punish whichever model happened to be running when the machine broke. They are classified as infrastructure errors, reported separately from wrong answers, and the suite stops hot-looping the affected unit rather than burning quota on a condition that will not improve. A wall-clock timeout is also reported as its own outcome, not folded into incorrectness.

11 · Reproducibility

Everything is open, and every run replays.

Every task, hidden test, gold patch, per-task Docker image, and the full grading harness are open source. Each run captures every step as a structured trace of model calls, tool calls, diffs, test results, and token usage, then writes a self-contained HTML transcript you can open in any browser, plus the exact command to replay it. Grading is deterministic and every run records the content hash of the task definition it was scored against, so a comparison is a query over recorded runs rather than a re-run, and a run scored against a since-edited task is flagged as stale instead of quietly compared. A run through a vendor CLI additionally records the harness and CLI version, the authentication mode and non-secret plan label, the requested and CLI-reported model, the requested and actual effort, and the raw redacted event stream. A field the CLI cannot report is recorded as unknown, never inferred.

The clock is a sanity bound, not a difficulty lever

Every frontier task carries a flat ten-hour timeout, following Terminal-Bench 4.0's move to a flat eight-hour agent timeout so that frontier models rarely or never time out. No run in the program has come near it. This replaced an earlier per-task calibration for a reason worth stating: tightening effective time does not make a benchmark harder, it converts wrong answers into timeouts, and one of the published reports shows exactly that happening as reasoning effort rises. So difficulty by the clock is reported analytically, pass@1-within-T computed from recorded durations and always shown alongside the full-budget score. No run is ever terminated by a time slice, which keeps the measurement about capability while still showing where the headroom is.

One caveat, stated plainly: host-run tasks do not yet pin CPU and memory. Every gate run so far executed on a single documented machine, and resource pinning comes before any cross-machine comparison is published.

Definitions

The terms, precisely.

pass@1

The fraction of tasks a model solves on its first attempt, with a solve decided by hidden tests, not judgment. It is the standard headline number in coding benchmarks, and it hides variance: a model that solves a task on half of its attempts still counts the same as one that always solves it, whenever the sampled attempt happens to pass.

pass@k

The probability that at least one of k independent attempts solves the task. It measures a model's ceiling: what you get if you can afford to retry and can recognize a correct answer when you see one.

pass^k

The probability that all k attempts solve the task: the dependability number. A team running a model inside automation cares about pass^k, not pass@k, because nobody is hand-picking the good attempt. On VulcanBench, pass^k is where cheap models have beaten frontier ones.

Reasoning effort

A per-request setting (minimal through max, depending on the provider) that controls how many thinking tokens a model spends before answering. More effort always costs more tokens and time; VulcanBench reports show it does not always buy more accuracy, and for some models accuracy falls as effort rises, mostly by converting finished wrong answers into timeouts.

Decontamination

Ensuring that no task in an eval suite could have appeared in a model's training data, on VulcanBench by building tasks from pull requests merged after every measured model's training cutoff, or by authoring them outright. Without it, a benchmark can measure memory instead of ability. Publishing a suite starts the clock on its own contamination, which is why every task carries a canary string and every suite is versioned.

Binary parity

A task format where the specification of the required behavior exists only inside a compiled binary. The agent is given a drifted written spec and a replacement implementation, and must recover the real behavior from the artifact until the two match byte for byte. It exists because defects written in readable source get found by reading.

Admission gate

A difficulty requirement a candidate task must clear before it joins a suite, measured against reference frontier models rather than asserted by the author. A suite gated this way has to prune tasks as models improve, and says so in its version number.

Model routing

Sending each class of task to the model and effort level that handles it best, instead of sending everything to one frontier model at maximum effort. A routing decision is only as good as the measurement behind it, which is what a stack benchmark exists to provide.

Hidden tests

Tests the model never sees, validated to fail on the code before the real fix and pass after it. They make grading deterministic: a patch passes or it does not, and no model judges another model.
