Claude Fable 5.2 across every effort level

115 runs of Anthropic’s Claude Fable 5.2 (claude-fable-5-2) in Claude Code on a Claude subscription, 23 tasks at each of five effort levels, Low to Max, from November 9 to 11, 2026. It solved all 115, the first column on the Frontier v4 leaderboard to solve every run at every level. Code quality carries 33% of the combined score and is judged for a human reader by Muse Spark 1.3 and GPT-6.1 Sol: Grok 4.6, the usual second judge, failed its calibration exam for this round, so GPT-6.1 Sol took the seat. Most other columns, Claude Fable 5.1 and Claude Opus 5.5 among them, are judged by Muse Spark 1.3 and Grok 4.6, so this page also shows a matched panel and Muse alone.

How the test works

  1. 1

    A retired program to rebuild

    Each of the 23 tasks is a legacy binary with a written specification and an issue. Its real behaviour departs from the specification in documented ways, and hidden tests check the rewrite against the binary.

  2. 2

    One attempt per task and level

    Claude Fable 5.2 works in Claude Code with the binary, the specification and the code, once per task at each effort level, inside a flat 3-hour bound, one task at a time.

  3. 3

    Tests and two judges score it

    Hidden tests give functional correctness. Two calibrated judges from labs other than Anthropic rate the code for a human reader and try to recover the documented departures.

  4. 4

    Scores, time and cost per level

    Each level gets a combined score, tasks passed, minutes and Claude Code’s own list-price cost.

Combined score = 50% functional correctness + 8.5% lint and complexity + 8.5% security + 33% Code quality, averaged over the 23 runs in each level, as on every other board column. Frontier Code quality is the reviewed layer plus intent recovery; it is never compared with Routine v1 Code quality.

How it works, and how that differs from Fable 5.1

Fable 5.2’s runs recorded summaries of its thinking (a run condition earlier Claude columns did not have) and every tool call. They are withheld because they describe the reference programs, but their structure is public in the session traces. Fable 5.1’s raw runs did not survive a host reset in September, so the comparison with it uses what both left in the same form: usage receipts, durations, fallback records and patches.

  • Effort controls how much it thinks. From Low to Max its output per task grows 8.7 times (16 thousand to 142 thousand tokens) and thinking rises from 48% to 67% of it. Fable 5.1’s output grew only 1.2 times, and its time stayed between 27 and 39 minutes at every level.
  • It is lean at low effort. At Low it used 19% of Fable 5.1’s output tokens, 17% of its time and 22% of its cost, and solved 23 tasks to Fable 5.1’s 19.
  • The patch does not grow. In every run it changed exactly one file, the module under repair, with a median of 97 to 113 added lines at every level, and kept its test harnesses in scratch space. Fable 5.1’s median patch grew from 112 to 190 lines with effort and added test files in 5 to 11 runs per level.
  • It reads the binary first. It inspected the reference binary in all 115 runs, at a median of its second tool call at Low and its seventh at Max, and the extra effort at higher levels goes to checking its rewrite against the binary rather than to a different answer.

Memorization check

Every Frontier v4 reference fix and test has been public on GitHub since late August 2026, about ten weeks before Claude Fable 5.2, and it solved every run, so the harness checked whether it was reciting answers.

  • Copying. Its solved patches reproduce 5.6% of the reference fixes’ distinctive lines verbatim, in the same range as six other models (4.4% to 5.7%), including Claude Opus 5, which was benchmarked before the fixes were public. A recited fix would score near 100%.
  • Working it out. It inspected the legacy binary before its first edit in 115 of 115 runs, against 43% to 67% for Claude Opus 5, Sonnet 5.5 and Haiku 5.5.
  • Recall. With no tools, asked to reproduce five reference fixes from memory, it answered each time that it did not remember the fix and wrote none; asked to fix one task blind, it declined to write a diff.

What Code quality measures

Every judge receives the same rubric, frozen by hash before any review. It names the reader it scores for: an engineer who has never seen the code, reads it top to bottom without running it, and must make a correct change in one sitting. It tells the judge that its own ease at parsing dense code is not evidence of readability. Six dimensions are scored 0 to 4 in half steps against written anchors: naming, presentation and intent form the human readability sub-score; structure, changeability and verifiability form the maintainability sub-score. Every score must cite an exact excerpt from the code and a concrete consequence for that reader. The host computes the sub-scores; the judge does no arithmetic.

The 33 points have three designed layers. The reviewed panel carries 24 points. An intent-recovery probe carries 9: the judge, given only the specification and the code, lists where the code departs from the specification, and a separate call matches that list against a frozen answer key, over the departures the submission passed tests for. The third layer, measured maintenance, is designed for 12 points but is not yet built, so the pre-registered 24 plus 9 split is in force.

Judges and calibration

Round v3.30 seated Muse Spark 1.3 (Meta) and Grok 4.6 (xAI), the panel of the Claude Opus 5.5 column, and both retook the calibration exam. Grok 4.6 failed one gate, g14_pair_2_1 (a pair of controls it scored 100 one way round and 50 the other), which the one-gate allowance does not cover, so it judged nothing. Muse Spark 1.3 passed every gate and judged Low to Extra-high under v3.30 and Max under v3.30.1. On the owner’s choice, GPT-6.1 Sol (OpenAI) through the Codex CLI at medium effort took Grok’s seat, passed every gate under v3.30.2, and judged Low to Extra-high under v3.30.2 and Max under v3.30.3, on byte-copied freezes of the same populations. Neither judge’s lab is Anthropic. The rubric, prompts, schemas, seed, repeats, gate allowance, weights and both judges’ pins equal the published v3.27 record, the Muse and Sol round that judged DeepSeek V4.1 Flash.

Before scoring a single submission, each judge reviews ten held-out programs that implement the same ledger specification, each five times in a seeded order, and twenty gates fixed in advance check that the judge sees the construct; a judge may miss at most one gate by at most half a point.

How it was run

  • The model. Claude Fable 5.2 as claude-fable-5-2 in Claude Code 2.1.321, pinned by hash with auto-updates off: the first release that names the model. Claude Code reports the serving model on every reply, and every reply in every run is claude-fable-5-2.
  • Harness settings. Permission mode auto, safe mode, no web access, a Claude subscription, refusal fallback on as for every Claude column (never used). Every integrity audit is clean: no web access, no benchmark data or answer-key paths. Every file written outside the workspace was scratch space under the temporary directory.
  • Thinking summaries recorded. Runs used --thinking-display summarized, so the traces keep summaries of the model’s thinking, a run condition earlier Claude columns did not have. The summaries are withheld from the public traces, which keep thinking as lengths only, because they describe the reference programs.
  • Five levels. Claude Code takes low, medium, high, xhigh and max for Claude Fable 5.2; the board’s Extra-high is xhigh.
  • Max waited for the usage limit. The Fable weekly usage limit was used up by the end of Extra-high. The first Max attempts were refused by the limit, did no work, hold no summary and are kept apart, not part of the population. Max ran from 23:15 PST on November 10, when the limit reset, to 13:28 PST on November 11.
  • From a tagged run worktree. Every run ran from bench/2026-11-09-fable52-frontier-v4, so every run summary carries a clean source block and records the frozen suite lock’s task hash.
  • Two receipts in two runs. Claude Code 2.1.321 can emit a second result receipt when a background task resumes a session after the model stops. It happened in two runs; their totals sum both receipts, as described under cost.
  • Where and how. The owner’s Mac, one task at a time, on November 9 to 11, 2026. Runs were not repeated, and effort labels are Claude Code’s own.

Evidence and reproduction

Public files contain all 115 run measurements, both judges’ six-dimension sub-scores and intent-recovery scores per run, the combined score from each judge alone, hidden behaviours fixed, integrity-audit verdicts, each run’s task hash, raw and thinking tokens, tool-call counts and list-price cost per run, five aggregates, every calibration gate value (Grok’s failed exam included), the exact judge protocol text, every operator recovery, the card’s per-level table, the Muse-alone table and source hashes. Each run’s Code quality is (0.24 × reviewed score + 0.09 × intent recovery) / 0.33, where both terms are the equal mean of the two judges. The combined score is 100 × (0.50F + 0.085Q + 0.085S + 0.33C / 100).
