All VulcanBench Frontier v4 reports

October 27, 2026 · Morgan Linton · 115 runs · Code quality protocol v3.28

Reflection Beam across every effort level

115 runs of Reflection Beam 1.0 (Beam-1.0-501B-A23B, 501B total and 23B active parameters, open weights) in Mirror CLI, Reflection’s own coding agent, on Reflection’s API: 23 tasks at each of Beam’s five reasoning levels, Low to Max. Code quality carries 33% of the combined score and is judged for a human reader under the same rubric, controls and gates as the other Frontier v4 reports, by Muse Spark 1.3 and GPT-6.1 Sol, the panel that judged DeepSeek V4.1 Flash, because Grok 4.6’s Cursor account was out of usage. At Low and Medium Beam often ends without changing any source file; those runs have no code to judge, count as failed tasks and are shown both ways below. Reflection publishes no Beam price, so this report has time and tokens but no cost. Reflection Beam takes its place on the Frontier v4 leaderboard with these caveats attached.

How the test works

  1. 1

    A retired program to rebuild

    Each of the 23 tasks is a legacy binary with a written specification and an issue. Its real behaviour departs from the specification in documented ways, and hidden tests check the rewrite against the binary.

  2. 2

    One attempt per task and level

    Reflection Beam works in Mirror CLI with the binary, the specification and the code, once per task at each effort level, inside a flat 3-hour bound, one task at a time.

  3. 3

    Tests and two judges score it

    Hidden tests give functional correctness. Two calibrated judges from labs other than Reflection rate the code for a human reader and try to recover the documented departures.

  4. 4

    Scores, time and tokens per level

    Each level gets a combined score, tasks passed, minutes and tokens. Reflection publishes no price for Beam, so there is no cost figure.

Combined score = 50% functional correctness + 8.5% lint and complexity + 8.5% security + 33% Code quality, averaged over the judged runs in each level, as on every other board column. Frontier Code quality is the reviewed layer plus intent recovery; it is never compared with Routine v1 Code quality.

Across every effort level

Reflection Beam ran every task once at each of the five reasoning levels its API takes (Extra-high is Beam’s xhigh), 23 tasks per cell, through Mirror CLI 0.1.1 on Reflection’s API, from October 23, 21:15 UTC, to October 25, 04:31 UTC, 2026, on the owner’s Mac in the local sandbox, one task at a time. Combined score weights are 50% functional correctness, 8.5% lint and complexity, 8.5% security and 33% Code quality, judged for a named human reader by Muse Spark 1.3 and GPT-6.1 Sol with a ground-truth intent-recovery probe.

Combined score

39.51 to 64.72

Combined score climbs with effort: 39.51 at Low, 44.79 at Medium, 55.01 at High, 64.72 at Extra-high and 63.92 at Max, over 11, 20, 23, 23 and 22 judged runs. Counting the runs that left no code as 0, Low is 18.90 and Medium 38.95.

Tasks passed

0, 0, 0, 4 and 6 of 23

Beam fully solves no task below Extra-high. Functional correctness over all runs is 0.9%, 10.8%, 35.6%, 56.5% and 58.3%; of the 231 hidden behaviours the tasks test for, it fixes 3, 26, 93, 130 and 134. No run reached the 3-hour bound.

No code at Low

12 of 23 Low runs

At Low, 12 runs ended with no source change (two empty patches, ten that only changed file modes or left scratch files), and 3 more at Medium. Two Low answers said the full reconstruction was beyond the session’s scope and two blamed a sandbox block that does not exist; see How it was run.

What Code quality measures

Every judge receives the same rubric, frozen by hash before any review. It names the reader it scores for: an engineer who has never seen the code, reads it top to bottom without running it, and must make a correct change in one sitting. It tells the judge that its own ease at parsing dense code is not evidence of readability. Six dimensions are scored 0 to 4 in half steps against written anchors: naming, presentation and intent form the human readability sub-score; structure, changeability and verifiability form the maintainability sub-score. Every score must cite an exact excerpt from the code and a concrete consequence for that reader. The host computes the sub-scores; the judge does no arithmetic.

The 33 points have three designed layers. The reviewed panel carries 24 points. An intent-recovery probe carries 9: the judge, given only the specification and the code, lists where the code departs from the specification, and a separate call matches that list against a frozen answer key, over the departures the submission passed tests for. The third layer, measured maintenance, is designed for 12 points but is not yet built, so the pre-registered 24 plus 9 split is in force. Frontier Code quality is therefore the reviewed layer plus intent recovery, and it is never compared with Routine v1 Code quality, which is scored on a different suite and population.

Judges and calibration

GPT-6.1 Sol in Grok 4.6’s seat. The scored panel is Muse Spark 1.3 (Meta) through the Muse CLI on its Standard tier, with its v3.4 settings and binary pin, and GPT-6.1 Sol (OpenAI) at medium effort through Codex CLI 0.159.0, its launcher and native binary pinned by sha256, with equal weight. Grok 4.6, the second judge for most columns, runs through Cursor, and a probe through the pinned Cursor CLI on October 24, 2026 still found the account out of usage. The owner kept GPT-6.1 Sol in the seat, as protocol v3.27 did for DeepSeek V4.1 Flash; this is the same pair, with the same settings and pins. Neither lab is Reflection. The Muse binary is a byte-identical backup of the v3.4 binary, matched by sha256 and re-checked before every stage. Every session is fresh, tools are disabled, the workspace is empty and solver labels are withheld. Muse’s identity is checked per call from the CLI’s own records; Codex does not record the serving model, so GPT-6.1 Sol’s identity is the model requested.

A different panel from the columns it is shown beside. Claude Opus 5.5, GPT-6.1 Sol and GPT-6 Astra’s own columns, like most columns on the board, are judged by Muse Spark 1.3 and Grok 4.6. Panels are not calibrated against each other, so Reflection Beam’s Code quality and combined score are not strictly comparable with theirs. GPT-6.1 Sol therefore judges a column it is shown beside; its own column was judged without it. Protocol v3.28 changes nothing in the rubric, controls, quirk keys, gates, repeats, seed or weights from v3.27; it applies the protocol to this population with this judge pair.

Before scoring a single submission, each judge reviews ten held-out programs that implement the same ledger specification: clear, compressed, compressed then auto-formatted, verbose with duplicated policy, needlessly abstracted, misleadingly commented, narrated with a comment on every line, a documented legacy quirk, an embedded instruction to give full marks, and hidden module state. Each program is reviewed five times in a seeded order. Twenty gates fixed in advance check that the judge sees the construct; a judge may miss at most one gate by at most half a point. Both judges retook the exam under v3.28 before any counted call.

How it was run

  • The model. Reflection Beam 1.0 through Reflection’s API as Beam-1.0-501B-A23B, the versioned id Mirror uses by default. The API’s model list shows only the alias Beam-501B-A23B, which the sweep checked before each level; requesting the versioned id keeps a later Beam version behind the alias from slipping in. Every inference in Mirror’s conversation database names the requested model, so model identity is harness-recorded.
  • Reflection’s own harness. Mirror CLI (reflection-mirror, Reflection’s open-source coding agent, Apache-2.0), version 0.1.1, an early beta, in its one-shot exec mode, pinned by exact version and a content hash of its installed package. It ran inside VulcanBench’s macOS outer sandbox with Mirror’s tool approvals automatic, since Mirror’s own sandbox workspaces need a microsandbox VM, and updates off. Mirror refuses to run until its usage notice is acknowledged and the folder trusted; at the owner’s approval each run had a private Mirror home with the notice acknowledged and only that run’s workspace trusted. Usage analytics were off and web tools absent, as for every harness on the board.
  • Five levels. Beam’s reasoning_effort takes low, medium, high, xhigh and max; the board’s Extra-high is xhigh.
  • A misleading sandbox note. Task files are staged without execute bits, as for every column on the board, and models that hit Permission denied on the legacy binary usually run chmod. When that happens in Mirror, it appends a note saying the sandbox denied access. Two Low runs ended saying the sandbox blocked the binary, which it does not, and two other Low answers said the full reconstruction was beyond the session’s scope. The adapter archived model messages and usage but not tool calls, so how often Beam saw the note cannot be counted.
  • A daily token limit. Reflection’s API has a daily token limit. It stopped the sweep on October 24 at 13:38 UTC after 13 Max tasks; the 1,200 attempts it cut short were set aside unscored and the sweep resumed after the 00:00 UTC reset. No finished run was affected. Six individual model requests failed in five runs and Mirror carried on.
  • From a tagged run worktree. Every run ran from bench/2026-10-23-beam-mirror-frontier-v4, so every run summary carries a clean source block and records the frozen suite lock’s task hash.
  • No timeouts, no overlapping jobs. Every run finished inside the flat 3-hour bound; the longest, Extra-high blendcore, took 57.1 minutes. A per-minute log watched for any other local benchmark job beside the sweep and recorded none.
  • Where and how. The local sandbox on the owner’s Mac, one task at a time, from October 23, 21:15 UTC, to October 25, 04:31 UTC. The API key was in the agent’s environment and the shell network was not isolated, as recorded on every run. Every integrity audit is clean: no web access, and no benchmark data or answer-key paths.
  • One attempt per task and level. Runs were not repeated.

Evidence and reproduction

Public files contain all 115 run measurements, both judges’ six-dimension sub-scores and intent-recovery scores per judged run, the combined score from each judge alone, the reason for every unjudged run, hidden behaviours fixed, integrity-audit verdicts, each run’s task hash and harness version, model calls, failed requests and raw tokens, five aggregates, every calibration gate value, the exact judge protocol text, every operator marker and source hashes. Each run’s Code quality is (0.24 × reviewed score + 0.09 × intent recovery) / 0.33, where both terms are the equal mean of the judges with a valid review, or the reviewed score alone when the run passed no quirk family. The combined score is 100 × (0.50F + 0.085Q + 0.085S + 0.33C / 100). The reproduction guide gives the public arithmetic checks and links the protocol document, the decision record, the Mirror CLI adapter and the code in the harness repository.

No human rated anything; the scores are model judgment for a human reader, not human validation. Hash checks bind the export to frozen files; they do not prove that judges were unbiased or that no training overlap exists.

Withheld: raw prompts and responses, submitted patches and reconstructed sources, the quirk answer keys (they describe hidden-test behaviour), reviewer session identifiers and usage receipts, Mirror conversation databases and solver traces, the 1,200 attempts cut short by the daily token limit, and host binary paths. Summed solver time is 20.21 hours; judging is excluded.
